<objective>
Install and configure the documentation and API-surface tooling for REL-03: typedoc for the generated reference (D-11) and api-extractor for the committed per-entry API reports (D-12), plus a runner script that also enforces the `@experimental`/`@beta` pairing (see decisions below). Wiring into `scripts/ci.sh`, committing the reports and turning enforcement on belong to plan 04-07 once every export is tagged.

Purpose: the tools must be proven against this repo's multi-entry package layout before the gate is switched on. This plan runs after the source-editing plans 04-02 to 04-04 so its smoke runs (build, api-extractor, typedoc) see a settled, tagged src tree, and it runs beside the docs-only plan 04-06, so it is the only plan in its wave allowed to run `npm install`.
Output: pinned devDependencies, `docs:api` / `api:check` / `api:update` scripts, typedoc.json, five api-extractor configs plus a shared base, `scripts/api.sh`.

Decisions applied (Claude's Discretion, D-10, D-12):
- One report per package entry point (five reports), because the root barrel omits the native presets and adapter helpers that D-08/D-09 classify; a single rolled-up report of `.` would not cover them.
- api-extractor 7.60.1 (verified while planning) recognises only `@public`, `@beta`, `@alpha`, `@internal` as release tags; a symbol tagged only `@experimental` still raises ae-missing-release-tag. To honour D-09/D-10 literally AND let the tool enforce tagging, every experimental declaration carries both `@experimental` and `@beta`. `scripts/api.sh` checks the pairing. TypeDoc treats `@beta` and `@experimental` as mutually exclusive modifiers and warns on every dual-tagged comment (verified with typedoc 0.28.20), so typedoc.json lists `@beta` in `excludeTags`; the rendered reference then shows only the Experimental badge.
- typedoc output (docs/api/) is gitignored and generated on demand.
</objective>
